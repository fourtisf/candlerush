# Deploying to the VPS

Target: a fresh Ubuntu/Debian box with a public IP, `candlerush.fun` pointing at it.

## Before you start

**DNS.** Two records, which are already in place on Hostinger:

| Type | Name | Content |
|---|---|---|
| A | `@` | your server's IP |
| CNAME | `www` | `candlerush.fun` |

`www` redirects to the apex at nginx. That is not cosmetic: a SIWE message names exactly
one domain, so a signature produced on `www.candlerush.fun` is rejected by an API configured
for `candlerush.fun`. One canonical host avoids the whole class of problem.

**The chain id.** `RHC_CHAIN_ID` has no default and the deploy refuses to run without it.
Take it from <https://docs.robinhood.com/chain>. A wrong value does not fail loudly — it
silently accepts SIWE signatures that were scoped to a different network.

## First install

```sh
ssh root@YOUR_IP

git clone --branch claude/new-session-2pbliw \
  https://github.com/fourtisf/candlerush.git /tmp/cr-bootstrap

RHC_CHAIN_ID=YOUR_CHAIN_ID DOMAIN=candlerush.fun EMAIL=you@example.com \
  bash /tmp/cr-bootstrap/deploy/vps-deploy.sh -y
```

Roughly five minutes. In order it will:

1. **Find and remove any previous install** — checkouts named `candlerush`/`candle-rush`
   anywhere on the root filesystem, and any `candle-rush-*` pm2 process. It prints what it
   found before deleting. Without `-y` it asks first.
2. Install Node, pnpm, pm2, Postgres, Redis, nginx. Adds 2G of swap if the box has under
   2GB of RAM, because the Next.js build is the memory spike and an OOM kill mid-deploy is
   an annoying way to find that out.
3. Clone into `/opt/candlerush`.
4. Create the database role and database with a freshly generated password.
5. Write `apps/api/.env` (mode `600`) and `apps/web/.env.local`, generating the JWT secret
   locally. `NEXT_PUBLIC_*` values are baked into the bundle at build time, so this has to
   happen before the build, not after.
6. Build engine → api → web, then `prisma migrate deploy`.
7. Start both processes under pm2 and enable the boot service.
8. Configure nginx and issue a Let's Encrypt certificate.
9. Curl both services and tell you if either is unhappy.

**The database is not dropped.** Only a checkout is removed. Balance is the sum of an
append-only ledger and it is the one thing in this system that cannot be reconstructed —
pass `--reset-db` if you genuinely want it gone, and it will still ask.

## What it looks like when it worked

```sh
pm2 status                                  # candle-rush-api, candle-rush-web: online
curl -s https://candlerush.fun/api/health   # {"ok":true,"engineVersion":1,"db":true,"redis":true}
curl -sI https://candlerush.fun | head -1   # HTTP/2 200
```

Then open the site, play a session as a guest, and confirm the P&L moves. Guest play needs
no wallet and no chain id — if that works, the renderer, the engine and the fixed-timestep
loop are all fine, and anything still broken is auth or the database.

## Routine redeploys

```sh
cd /opt/candlerush && bash deploy/update.sh
```

Pulls, rebuilds, migrates, reloads. It does not touch `.env` and it does not delete data.

If a deploy changes gameplay, `ENGINE_VERSION` must be bumped in the same commit. Sessions
still open across the restart are then rejected on submit with `ENGINE_VERSION_MISMATCH`,
which is correct: a tape recorded against the old engine replays to garbage on the new one,
and the player losing one run is much better than the ledger gaining a fake number.

## Rolling back

```sh
cd /opt/candlerush
git log --oneline -10
git reset --hard <sha> && bash deploy/update.sh
```

Migrations do not roll back. `0_init` is additive, so an older build runs against the newer
schema; that stops being true the first time a migration drops or renames a column, and at
that point a rollback needs a down-migration written by hand.

## Layout on the box

```
/opt/candlerush                app, cloned at the deploy branch
/opt/candlerush/apps/api/.env  secrets, mode 600 — not in git, not regenerated by update.sh
/opt/candlerush/logs/          pm2 stdout and stderr
/etc/nginx/sites-available/candlerush
```

## When something is wrong

```sh
pm2 logs candle-rush-api --lines 100
pm2 logs candle-rush-web --lines 100
nginx -t && systemctl status nginx
sudo -u postgres psql candlerush -c '\dt'
redis-cli ping
```

**The API will not start.** Almost always the environment. It validates everything at boot
and names the offending variable; `pm2 logs candle-rush-api` will have it. `RHC_CHAIN_ID`
missing and `JWT_SECRET` under 32 characters are the two common ones.

**Sign-in fails with `BAD_DOMAIN`.** The browser is on a hostname that is not
`SIWE_DOMAIN` — usually `www`, meaning the redirect is not in place, or the site is being
reached over plain HTTP.

**Sign-in fails with `BAD_NONCE`.** Nonces live in Redis for five minutes and are consumed
on use. Either Redis restarted mid-flow, or the message is being submitted twice.

**Every session is rejected as `TOO_SLOW`.** Check the clock: `timedatectl`. The wall-clock
window is measured against the server's own time.

**One player's rate limit is hitting everyone.** `X-Forwarded-For` is not reaching Fastify,
so every request looks like `127.0.0.1`. Check the `proxy_set_header` lines in the nginx
site — they are what make the per-IP limit mean anything.

## Hardening worth doing before you tell anyone the URL

```sh
ufw allow OpenSSH && ufw allow 'Nginx Full' && ufw --force enable
```

Postgres and Redis both bind to localhost only in this setup, and nothing in the app
listens on a public port except through nginx. Worth confirming with `ss -tlnp` rather than
assuming.
